# 空间（Space）：把 Bot 和群按部门分组展示

- 日期：2026-10-21（草案，待维护者确认）
- 相关：—

## 为什么

一家公司一个团队，Bot 会越建越多：市场、技术、运营的 Bot 和群混在同一条侧栏里，越翻越乱。用户要的只是「各看各的一摊」——数据、记忆、能力本来就该共享，不需要真正的多租户。

真正的隔离方案（每团队一个实例、网关登录）对团队内部使用成本太高：每个实例多吃一份内存，前面还得加一层网关。而 DSH 本身也不向插件提供用户身份（浏览器令牌只认「主人」），插件无法按登录者区分视图。所以做展示层分组：一份数据，多个视角。

名字选「空间（Space）」而不是「分组」，避免和「群聊」「团队」撞词。

## 已定的行为（草案）

- `state.spaces` 存空间表：`{ id, name, color?, createdAt }`。Bot 和群各有一个可选 `space` 字段，值为空间 id。
- 侧栏按空间分节：空间名作节标题，可折叠；没有空间的 Bot 和群落在最上面的「未分组」节。置顶（pin）的条目仍在各自节内排前。
- 空间在 Settings 里管理：新建、改名、换色、删除。删空间只把成员退回「未分组」，不删除任何 Bot 或群。
- 新建 Bot / 群的表单可选空间；`update_bot` 和 `update_group` 增加可选 `space` 参数，Main Bot 也能移动成员。给 Main Bot 增加 `create_space` / `update_space` / `delete_space` 工具。
- 跨空间的 `message_bot`、`@` 点名、混编进同一个群，照旧允许——同一家公司，协作不该被分组拦住。
- 空间数量给一个上限（32），命名规则与群名相同。
- 迁移：旧团队没有 `spaces` 字段，全体成员落在「未分组」，行为不变。

## 空间 PIN 与远程入口（2026-10-22 追加，草案）

用户想要的「每个部门一个口令」折成两层：

- 空间可设可选 PIN（scrypt 加盐哈希存在 `space.pin`，只有哈希，接口只回 `locked` 布尔）。侧栏里锁定空间只显示标题与锁图标，点开输入 PIN 后展开；解锁状态记在浏览器 localStorage，不漫游。`check-space-pin` 端点验证 PIN：给 id 答是否匹配，只给 PIN 则返回它所属的空间。
- 本机（loopback）照旧走 dsh 自身的 token —— 插件不能也不应关掉 dsh 的认证；用不带 `--no-open` 启动即可免输。
- 对外共享走 `ds-bot/dev/remote-gate.mjs`：一个小型 Node 反向代理监听 LAN 地址，远程访客先过 PIN 表单（任意空间 PIN 均可进门），进门时代理注入上游 token 换到的 cookie，并用 `ds-bot-unlocked` cookie 把对应空间解锁进侧栏。带按 IP 的失败限流。

## 不做什么

- 不做任何**真正**的访问控制：PIN 只挡住侧栏一层的展示，数据仍在同一 roster/sessions/工作区；会开 DevTools 或翻 DSH 原生会话列表的人照样看全。这是整理与遮挡，不是隔离。
- 不做按空间的记忆、密钥、能力、用量、工作文件夹——这些仍归整个团队。
- 不拦 Bot 跨空间发消息、@ 或入群。
- DSH 自己的会话列表不归本插件管；空间只作用于 DS Bot 界面。

## 已知限制

- 想让「某部门看不到别部门」的用户得不到隐私：会话仍在同一个 sessions 池，DSH 原生界面也能翻到。要真隔离仍需每团队一个实例。
- 空间是手动整理，不做自动归类；「未分组」里的 Bot 多了同样会长。
